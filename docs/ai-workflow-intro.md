# AI 编程助手工作流 · 介绍与使用指南

本仓库是一套**零第三方插件依赖的风险分级 AI 编程工作流模板**：所有方法论（规范驱动变更、TDD、计划书、子代理审查等）都以原生资产内联在仓库里，**Claude Code 与 Codex 双运行时可用**，两套助手共享同一份变更数据层（`openspec/`）和知识层（`.ai/`），不分叉。

- Claude Code 自动读取 [`CLAUDE.md`](../CLAUDE.md) 总纲，技能在 `.claude/skills/`
- Codex 自动读取 [`AGENTS.md`](../AGENTS.md) 总纲，技能在 `.codex/skills/`
- 权威规格：[`openspec/specs/risk-tiered-ai-workflow/spec.md`](../openspec/specs/risk-tiered-ai-workflow/spec.md)

```text
                ┌─ 快速：探索事实 → 直接修改 → 针对性验证 → 汇报
用户提需求 ──▶ 分类 ─┼─ 标准：Open 四件套 → 一次确认 → Build → 综合 Verify → Archive
                └─ 严格：Open → 确认 → Design → 确认 → Build(TDD) → Verify(双阶段) → Archive
```

## 一、核心机制：先按风险分流，再选流程

任何变更开始前，助手先用一句话说明所选模式与理由；无法可靠分类时自动升级到更严格的模式。**用户可以要求升级，任何人都不得把严格任务降级。**

| 模式 | 适用条件 | 流程路径 | 确认次数 |
|---|---|---|---|
| **快速** | 只维护已有事实的 Markdown、纯文本、注释或机械格式，不影响运行时、API/Schema、配置语义、安全合规、工作流治理或发布 | 探索事实 → 直接修改 → 针对性验证 → 汇报 | 0（清晰请求即授权） |
| **标准** | 低到中风险运行时代码变更 | Open 一次产出四件套 → 一次确认 → Build → 综合 Verify → Archive | 1 |
| **严格** | 权限认证、资金账务、删除/迁移、数据库 Schema、并发一致性、跨服务或公开运行时契约、工作流治理、破坏性操作、大范围重构 | Open → Design → Build → Verify → Archive 完整五阶段 | 2（四件套 + 计划） |

### 快速模式

- 不创建 OpenSpec 四件套、计划、feature 分支或 worktree，不用 TDD、子代理或归档，默认不提交 Git。
- 核对权威事实后直接修改，现跑内容/链接/示例/格式校验并检查完整 diff。
- 发现必须改变行为或契约才能完成时，立即停止并升级到标准/严格。

### 标准模式

- Open 一次产出可执行四件套：`proposal.md`（记`模式: 标准`）、`specs/<能力>/spec.md`（delta）、`design.md`、`tasks.md`（精确文件、步骤、验证命令）。
- **唯一一次实施前确认**同时覆盖范围、设计、任务与本地整合策略；确认后连续执行 Build → Verify → Archive，不再逐阶段打断（范围变化、验证失败、争议、外部副作用授权除外）。
- 状态：`待确认计划 → 构建中 → 待验证 → 待归档 → 已归档`；不创建独立 `openspec/plan`。
- 默认 feature 分支；仅脏工作区、并行实现、高冲突或用户要求时才用 worktree。小任务主会话直执，完成后至多一次全 diff 综合审查。

### 严格模式

- 四道硬门禁：四件套未确认不写计划（G1）、计划未确认不写代码（G2）、测试不全绿不交棒（G3）、两阶段审查未过不归档（G4）。
- 八态状态机：`草稿 → 待确认规范 → 设计中 → 待确认计划 → 构建中 → 待验证 → 待归档 → 已归档`。
- 独立计划书落盘 `openspec/plan/<变更名>.md`；默认隔离 worktree、运行时 TDD、任务级审查 + Verify 双阶段独立审查（规格符合性、代码质量两个关注面）。

## 二、优点：这套流程解决了什么问题

### 1. 流程成本与风险相称

改一行文档不必走五阶段门禁，动权限认证也绝不允许走捷径。旧版"所有变更一律五阶段"的重量流程已被治理规则和校验器明确禁止回退——校验器会检测"再次强制统一重流程"的回归并报错。

### 2. 单一状态真源，任意断点续传

标准/严格变更的状态只看 `openspec/changes/<变更名>/proposal.md` 的`状态:`字段，进度看 `tasks.md`。会话中断、换人、换助手（Claude ↔ Codex），新会话读取这两个文件即可从断点精确继续，不依赖对话历史。

### 3. 单确认点设计，减少打断

标准模式把规格、设计、任务、整合策略打包成一次确认；确认后助手连续执行到归档。相比每阶段都停下来等回复，用户只需要在关键决策点出场。

### 4. 硬门禁防跳步

严格模式 G1–G4 由技能与总纲双重声明，配合结构校验器兜底：模式定义缺失、快速模式被错误要求四件套、标准模式被强制独立计划等回归都会使校验失败。

### 5. 审查完整性可验证

完整审查由 `.ai/rules/review.md` 契约约束：

- **manifest 冻结与陈旧检测**：审查前主会话冻结受影响仓库快照（`.ai/tools/review_manifest.py freeze`，产物在 `.ai-local/reviews/<变更>/`）；reviewer 在读取范围前和形成结论前各跑一次 `verify`，任一 `STALE` 立即停止——杜绝"审的是旧代码、报的是新结论"。
- **finding 台账固定字段**：每条 finding 必须有证据、精确位置、可观察影响、最小修复与复验命令；Critical/Important 只有 resolved / not-an-issue / 用户明示的 accepted-risk 才解除阻断。
- **最小修复沿用授权**：已确认范围内的最小修复不再重新确认；修复后只对 manifest delta 差异复审，不无证据重读未变化范围。

### 6. 双运行时共享不分叉

`openspec/`（变更数据）与 `.ai/`（知识层）是 Claude 与 Codex 的共享正文来源；两侧技能做字节级镜像校验（仅豁免声明的适配差异）。在一侧改了流程，另一侧的分叉会被 `validate-workflow.sh` 抓住。

### 7. 知识沉淀飞轮

`.ai/` 三层知识：`kb/`（稳定架构与项目卡）、`memory/`（踩坑记录，坑解决后即时追加）、`rules/`（路由表与审查契约）。归档时执行知识三写（memory 归整、kb 同步、rules 更新），踩过的坑自动变成下次会话的起点。

### 8. 用户保护与显式授权底线（所有模式不可削弱）

- 用户未提交修改永不覆盖；目标文件与未提交修改重叠时先隔离、绕开或请求决定。
- 推送、PR、强推、删除未合并工作等外部/破坏性动作必须单独授权。
- 范围扩大或风险升级即暂停并重新确认；完成声明前必须现跑相称验证并读取退出结果。
- 变更可经**用户明确决定**进入`已取消`终态（助手只能建议，不能自行取消）；取消的 delta 不合并、不复活，只作历史记录。

### 9. 可移植安装

`scripts/` 提供把整套工作流装进任意目标项目的安装器，装后自检全绿才退出；升级走台账驱动的事务性路径，失败自动回滚（详见 `.ai/rules/index.md` 的安装器契约条目）。

## 三、使用方法

### 1. 起步：直接用本仓库，或安装到已有项目

```bash
# 方式一：克隆本仓库作为模板
git clone <本仓库地址> && cd ai_agent

# 方式二：安装到已有项目（装后自检全绿才退出）
bash scripts/install-workflow.sh /path/to/your-project          # 首次安装
bash scripts/install-workflow.sh /path/to/your-project --force   # 覆盖升级（旧资产备份为 *.bak；memory 永不覆盖）
bash scripts/install-ai-workflow.sh --help                       # 便携安装器（支持 --upgrade 台账驱动升级）
```

装完后填写目标项目 `openspec/project.md` 的项目上下文，重启 AI 会话即可。

### 2. 发起变更：你只需要自然语言

| 你说 | 助手做 |
|---|---|
| "开始做一个用户导出 CSV 的功能" | Open：核对权威事实 → 分类（标准/严格）→ 产出四件套 → 等你确认 |
| "确认计划，开工"（标准）/"确认规范，出计划"（严格） | Build：逐任务实现（运行时变更走 TDD），tasks 勾选、测试全绿 |
| "构建完成，审查" | Verify：标准=一次全 diff 综合审查；严格=双阶段独立审查 + 终验证据 |
| "审查通过，归档" | Archive：delta 并入主 specs、知识三写、目录移入 `openspec/archive/`、分支收尾 |
| "帮我补一段接口说明文档" | 快速模式：直接改 + 现跑校验 + 汇报，不打断你 |

### 3. 断点恢复

新会话开场直接说"继续 <变更名>"或描述需求即可。助手按总纲先读 `openspec/changes/<变更名>/proposal.md` 的`模式:`与`状态:`、再读 `tasks.md`，从断点继续，不重建已有变更。

### 4. 取消变更

对任一未归档变更明确说"取消这个变更"。助手会把`状态:`置为`已取消`、记录一句原因、目录移入 `openspec/archive/`；feature 分支、worktree 与未提交修改的去留由你明确指示，不会自动删除。

### 5. 校验与本地防护

```bash
bash scripts/validate-workflow.sh                  # 全量结构校验（默认）
bash scripts/validate-workflow.sh --fast           # 秒级 core 校验（标准模式 Verify 终验分层用）
bash scripts/validate-workflow.sh --require-openspec   # 严格模式 / 治理资产变更全量门禁
git config core.hooksPath scripts/hooks            # （自愿）pre-push 秒级防护，FAIL 阻断推送
```

分层规则：标准模式内容变更的 Verify 用 `--fast` + 目标/回归测试，归档后跑全量；严格模式及触及工作流入口、技能、校验器、安装资产的变更始终全量。

### 6. 技能一览（13 个，无需安装插件）

**5 个阶段编排器**

| 技能 | 触发时机 |
|---|---|
| `open` | 新需求、修改请求或需要风险分类时 |
| `design` | 严格模式四件套已确认、需要独立实现计划时 |
| `build` | 标准/严格方案已获实施确认、执行实现时 |
| `verify` | 构建完成、需要审查与终验时 |
| `archive` | 审查终验通过、合并规格与收尾时 |

**8 个支撑技能**（只在触发条件命中时加载）

| 技能 | 触发时机 |
|---|---|
| `tdd` | 实现或修改可执行运行时行为之前 |
| `code-review` | 变更到达审查边界、合并前需独立判断，或需核实审查意见时 |
| `systematic-debugging` | 遇到缺陷、测试失败或意外行为，提出修复方案之前 |
| `verification` | 即将声称"完成/已修复/测试通过"之前 |
| `git-worktrees` | 需要工作区隔离、有未提交修改、并行冲突，或严格模式实施前 |
| `parallel-agents` | 2 个以上互相独立、无共享状态、无顺序依赖的任务 |
| `subagent-driven` | 会话内多个边界独立的实现任务，或严格模式需隔离实现与审查判断 |
| `writing-skills` | 创建或修改技能时 |

宿主插件技能与仓库技能职责重叠时，**以仓库技能为准**；插件技能只补空缺。

### 7. 知识库写入

| 目录 | 用途 | 写入时机 |
|---|---|---|
| `.ai/kb/` | 模块功能介绍、架构设计、项目卡 | 权威事实变化并经核对后；Archive 必写 |
| `.ai/memory/` | 踩坑记录，按模块一文件，追加式 | 坑解决后即时写；Archive 归整 |
| `.ai/rules/` | 硬约束与路由表（`index.md`） | 路由或治理规则变化时 |

## 四、避坑备忘

- openspec 的 Requirement 正文必须含英文关键字 **SHALL** 或 **MUST**（纯中文"应"会被 CLI 判错），推荐"系统 SHALL …"中英混排。
- Python 项目初始化即写 `.gitignore`（`__pycache__/`、`*.pyc`），避免生成物误入提交与安装资产。
- 提交按可独立回滚的职责单元组织，不要求每个 checklist 条目至少一次提交。
