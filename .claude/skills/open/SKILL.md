# Open——风险分类与需求入口

先分类，再行动。开始时向用户用一句话说明所选模式与理由；未知或边界不清至少升级到标准，严格条件不得降级。

## 分类契约

| 模式 | 可观察条件 | Open 的出口 |
|---|---|---|
| 快速 | 只维护已有事实的文档、纯文本、注释或机械格式，且不改变运行时、API/Schema、配置语义、安全合规、工作流治理或发布行为 | 直接修改、验证、汇报；无 OpenSpec 状态 |
| 标准 | 低到中风险运行时代码变更，未命中严格条件 | 一次产出可执行四件套，`模式: 标准`、`状态: 待确认计划` |
| 严格 | 权限、资金、删除/迁移、Schema、并发、跨服务或公开运行时契约、工作流治理、破坏性操作、大范围重构 | 产出四件套，`模式: 严格`、`状态: 待确认规范` |

用户可要求升级。分类时只看影响，不看扩展名：修改安全规范的 Markdown 仍是严格；根据已实现 Controller 补接口说明可以是快速。

## 快速模式

用户清晰的请求就是实施授权，流程固定为：

1. 探索权威事实和目标文件，检查是否与用户未提交修改重叠。
2. 直接做最小修改。
3. 现跑内容、结构、链接、示例、格式或事实来源校验，并检查完整 diff。
4. 汇报修改与证据。

不创建 proposal/spec/design/tasks 或独立 plan；不切 feature、不建 worktree、不用 TDD、子代理或 Archive；默认不提交或合并。

若探索发现文档目标与实现冲突，或必须改行为/API 才能完成，停止快速模式，保留证据并按新风险进入标准或严格。升级后的确认完成前不扩大修改。

## 标准模式

先读 `.ai/rules/index.md` 并按命中项探索代码。一次创建：

- `proposal.md`：`模式: 标准`、`状态: 待确认计划`、Why/What Changes/Impact；草拟过程不暴露中间状态。
- `specs/<能力>/spec.md`：ADDED/MODIFIED/REMOVED Requirements；每条至少一个 WHEN/THEN Scenario。
- `design.md`：关键决策、替代方案、风险与边界。
- `tasks.md`：可直接执行的职责单元，写精确文件、步骤、验证命令、预期结果和本地整合策略。

自审规格覆盖、失败路径、任务可执行性和用户修改保护；完成后把状态直接置为`待确认计划`，请求唯一一次实施前确认。该确认同时覆盖范围、设计、任务与明示的本地整合策略；不得另建 `openspec/plan` 或再调用 design。

## 严格模式

读取 ai-kb、探索代码、澄清会改变范围的未知项，再创建同样的四件套。`tasks.md` 此时是范围清单，不替代独立实现计划。

自审 Requirements/Scenarios、边界和错误路径，状态置为`待确认规范`并请求第一次确认。确认前不写独立计划或实现；确认后交 design。

## 恢复与底线

- 已有 proposal 时先读`模式:`、`状态:`和 tasks，不重建变更；旧 proposal 没有模式时按影响重新分类并补字段。
- 范围不清且探索不能消除时询问用户；不得猜测为快速。
- 任何模式都保护用户修改，外部/破坏性动作单独授权，完成声明必须有新鲜验证证据。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| “只是 Markdown，所以快速” | 先判断是否改变契约、治理或发布语义 |
| 快速模式先建四件套以防万一 | 未命中标准/严格就直接交付 |
| 标准模式再写独立 plan | 可执行 tasks 已承担计划职责 |
| 不确定时猜低风险 | 至少升级到标准并探索 |
