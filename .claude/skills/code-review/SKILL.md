# 请求代码审查

派发代码审查子代理，在问题级联之前抓住它。审查者拿到的是精确构造的评估上下文——绝不是你会话的历史。

**核心原则：** 早审查，勤审查。

（源技能附有 code-reviewer.md 审查者模板，未随本仓库迁移；其提示要素与输出格式已内联于下文"如何请求"。）

## 何时请求审查

**强制：**
- 子代理驱动开发中的每个任务之后
- 完成重大特性之后
- 合并到 main 之前

**可选但有价值：**
- 卡住时（换一双眼睛）
- 重构前（基线检查）
- 修复复杂缺陷后

## 如何请求

**1. 取 git SHA：**
```bash
BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
HEAD_SHA=$(git rev-parse HEAD)
```

**2. 派发代码审查子代理：**

派发一个 general-purpose 子代理，提示中填入以下上下文清单（占位符）：

- `{DESCRIPTION}`——你构建了什么的简短摘要
- `{PLAN_OR_REQUIREMENTS}`——它应当做什么（计划文件路径、任务文本或需求）
- `{BASE_SHA}`——起始提交
- `{HEAD_SHA}`——结束提交

审查者提示的核心要素：

- **角色：** 资深代码审查者，专长软件架构、设计模式与最佳实践；对照计划/需求审查已完成的工作，在问题级联前识别它们
- **只读审查：** 不以任何方式改动工作树、索引、HEAD 或分支状态；只用 `git show`、`git diff`、`git log` 检查历史；需要别的版本的工作副本时，检出到独立的临时目录（如 `git worktree add /tmp/review-<SHA> <SHA>`）——绝不在本检出上移动 HEAD
- **对照规格逐条：** 实现是否匹配计划/需求？偏差是合理的改进还是问题性偏离？计划的功能是否全部在场？与计划有重大偏离时单独标记，让实现者确认是否有意为之；发现问题出在计划本身而非实现时，直说
- **找缺陷：**
  - 代码质量：关注点分离干净？错误处理得当？该有的类型安全？DRY 而不过早抽象？边界情形处理了？
  - 架构：设计决策合理？可扩展性与性能合理？安全顾虑？与周边代码干净集成？
  - 测试：测试验证真实行为而非 mock？边界覆盖？该有的集成测试？全部通过？
  - 生产就绪：改了 schema 有迁移策略？考虑向后兼容？文档完整？无明显缺陷？
- **校准：** 按实际严重度分类——不是所有问题都是 Critical；列问题之前先肯定做得好的部分（准确的肯定让实现者信任其余反馈）
- **输出 findings 列表**，固定格式：
  - 优点（具体到 file:line）
  - 问题：**Critical（必须修）**——缺陷、安全、数据丢失、功能破坏；**Important（应修）**——架构问题、缺失功能、错误处理差、测试缺口；**Minor（可有可无）**——代码风格、优化机会、文档润色。每条含：file:line 引用、什么错了、为何要紧、怎么修（若不显然）
  - 建议面向代码质量、架构或流程的改进
  - 结论：**可否合并？（是 / 否 / 修复后可）**＋一两句技术评估理由
- **不做：** 没查就说"looks good"；把 nitpick 标成 Critical；对没实际读过的代码给意见；含糊其辞（"改进错误处理"）；回避明确结论

**3. 处置反馈：**
- Critical 问题立即修
- Important 问题继续前修
- Minor 问题记下待办
- 审查者错了就据理反驳（见下文"接收代码审查"）

## 示例

```
[刚完成任务 2：添加校验函数]

你：继续之前，先请求代码审查。

BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | awk '{print $1}')
HEAD_SHA=$(git rev-parse HEAD)

[派发代码审查子代理]
  DESCRIPTION: 加了 verifyIndex() 与 repairIndex()，含 4 类问题
  PLAN_OR_REQUIREMENTS: docs/plans/deployment-plan.md 的任务 2
  BASE_SHA: a7981ec
  HEAD_SHA: 3df7661

[子代理返回]：
  优点：架构干净，测试是真的
  问题：
    Important: 缺进度指示
    Minor: 报告间隔的魔法数字（100）
  结论: 可以继续

你：[修进度指示]
[继续任务 3]
```

## 常见自我合理化

| 借口 | 现实 |
|--------|---------|
| "我自己看 diff 就行，不用派审查者" | 你是协调者——内联看 diff 烧掉你继续推动工作所需的上下文窗口。派审查子代理：diff 与评估活在它的上下文里，只有发现清单回到你这里。 |
| "审查者需要我会话的全部历史才能理解这个改动" | 递给它精确构造的上下文，绝不是你的会话历史。这让审查者盯住工作产物，而不是你的思考过程。 |

## 红旗

**绝不：**
- 因为"很简单"就跳过审查
- 忽视 Critical 问题
- 带着未修复的 Important 问题继续
- 与有效的技术意见争执

**审查者错了时：**
- 用技术推理反驳
- 出示证明其有效的代码/测试
- 请求澄清

# 接收代码审查

## 概述

代码审查需要技术评估，不是情绪表演。

**核心原则：** 先验证再实施。先问清再假设。技术正确性高于社交舒适。

## 响应模式

```
收到代码审查意见时：

1. 读：完整读完意见，不即时反应
2. 理解：用自己的话复述要求（或提问）
3. 验证：对照代码库现实核查
4. 评估：对本代码库技术上行得通吗？
5. 回应：技术性确认，或有理反驳
6. 实施：一次一条，逐条测试
```

## 禁止的回应

**绝不：**
- "您说得对！"（对指令文件的明确违反）
- "好观点！"/"精彩意见！"（表演性）
- "我马上实现"（验证之前）

**应当：**
- 复述技术要求
- 提澄清问题
- 审查者错了就用技术推理反驳
- 直接开工（行动 > 言辞）

## 处理含糊意见

```
若任一条目含糊：
  停——先不实施任何东西
  就含糊条目请求澄清

为什么：条目之间可能相关。部分理解＝错误实施。
```

**示例：**
```
用户："修 1-6"
你理解 1、2、3、6，4、5 含糊。

❌ 错：立刻实施 1、2、3、6，4、5 以后再问
✅ 对："我理解第 1、2、3、6 条。动手前需要澄清第 4、5 条。"
```

## 按来源分别处理

### 来自用户
- **可信**——理解后即实施
- 范围不清时**照样要问**
- **不做表演性认同**
- **直接行动**或技术性确认

### 来自外部审查者
```
实施之前：
  1. 查：对本代码库技术正确吗？
  2. 查：破坏既有功能吗？
  3. 查：当前实现如此是有原因的吗？
  4. 查：所有平台/版本上都行得通吗？
  5. 查：审查者了解完整上下文吗？

若建议看来是错的：
  用技术推理反驳

若无法轻易验证：
  直说："没有 [X] 我无法验证。要我 [调查/询问/继续] 吗？"

若与用户的既有决定冲突：
  停下，先与用户讨论
```

**用户的规矩：** "外部意见——保持怀疑，但仔细核实。"

## "专业化"功能的 YAGNI 检查

```
若审查者建议"规范地实现"：
  grep 代码库查实际用法

  若无人使用："这个端点没人调用。删掉它（YAGNI）？"
  若有使用：那就规范地实现
```

**用户的规矩：** "你和审查者都向我汇报。我们不需要这个功能，就别加。"

## 实施顺序

```
对多条目意见：
  1. 先澄清一切含糊项
  2. 然后按此顺序实施：
     - 阻断性问题（破坏、安全）
     - 简单修复（笔误、导入）
     - 复杂修复（重构、逻辑）
  3. 每条修复单独测试
  4. 验证无回归
```

## 何时反驳

以下情况反驳：
- 建议破坏既有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（没人用的功能）
- 对本技术栈技术上行不通
- 存在历史/兼容性原因
- 与用户的架构决定冲突

**怎么反驳：**
- 用技术推理，不用防御姿态
- 提具体问题
- 引用可运行的测试/代码
- 涉及架构时请用户介入

**若你不惯于把反驳说出口：** 说出这层顾虑，然后把你看出来的问题告诉用户。用户会欣赏你的诚实。

## 确认正确的意见

意见确实正确时：
```
✅ "已修。[改动内容的简短描述]"
✅ "抓得准——[具体问题]。已修于 [位置]。"
✅ [直接修掉，在代码里体现]

❌ "您说得对！"
❌ "好观点！"
❌ "感谢抓住这个！"
❌ 感谢 [任何东西]
❌ 任何形式的感谢表达
```

**为什么不感谢：** 行动说话。直接修。代码本身就表明你听进了意见。

**若你发现自己正要写"感谢"：** 删掉。改说修了什么。

## 得体地纠正自己的反驳

反驳之后发现是自己错了：
```
✅ "你是对的——我查了 [X]，它确实 [Y]。现在实施。"
✅ "核实过了，你正确。我最初的理解错了，因为 [原因]。修复中。"

❌ 冗长的道歉
❌ 辩解自己为何反驳
❌ 过度解释
```

事实性地陈述纠正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演性认同 | 陈述要求，或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量处理不测试 | 一次一条，逐条测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实施 | 先澄清全部条目 |
| 无法验证仍硬上 | 陈述局限，请求指示 |

## 真实示例

**表演性认同（坏）：**
```
审查者："删掉遗留代码"
❌ "您说得对！我来删……"
```

**技术验证（好）：**
```
审查者："删掉遗留代码"
✅ "核查中……构建目标 10.15+，这个 API 要 13+。为了向后兼容需要遗留路径。当前实现的 bundle ID 错了——修掉它，还是放弃 13 以下支持？"
```

**YAGNI（好）：**
```
审查者："规范地实现指标追踪，带数据库、日期过滤、CSV 导出"
✅ "grep 过代码库——没有任何地方调用这个端点。删掉（YAGNI）？还是有我漏掉的用法？"
```

**含糊条目（好）：**
```
用户："修 1-6 条"
你理解 1、2、3、6，4、5 含糊。
✅ "理解 1、2、3、6。实施前需要澄清 4 和 5。"
```

## GitHub 线程回复

在 GitHub 上回复行内审查评论时，在评论线程里回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要发成 PR 顶层评论。
