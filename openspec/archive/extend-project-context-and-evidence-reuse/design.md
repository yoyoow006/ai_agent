# 设计：通用项目上下文与验证证据复用

## 目标

在保持源仓库无业务事实、工具只读和 OpenSpec 唯一状态真源的前提下，让目标项目能登记更完整的技术上下文，并在安全条件下复用验证证据。

## 决策

### 1. 项目卡模板承载语义，registry 承载机械事实

模板帮助目标维护者描述职责、非职责、入口、关系和边界，但不把正文变成机器解析对象。registry 继续保存可校验的路径、依赖、应用、业务词和验证声明。这样避免用一个 JSON 表达所有业务语义，也避免从自由文本猜测事实。

### 2. 多仓依赖只做声明和闭环校验

`dependencies` 只允许引用同 registry 中的项目名，并拒绝自依赖、重复和循环。查询输出直接依赖，不递归展开传递闭包；影响分析仍需按实际契约和代码核实。这个设计足以支持“先找直接上游/下游”的路由，同时避免把声明图误当成真实构建依赖。

### 3. 验证命令是入口描述，不是执行授权

`verification.build_command` 和 `test_command` 是目标项目声明的本地命令示例。`project_facts.py` 仅输出它们，不执行。实际执行仍受当前任务授权、用户确认和外部副作用规则约束。

### 4. `verified_commit` 表示证据基线，不表示当前任务通过

工具只比较登记 commit 与当前项目 Git HEAD，输出 current、drifted 或 unavailable。current 只说明验证基线与 HEAD 一致，不说明工作区无局部修改，也不免除当前任务的目标/回归验证；drifted 或 unavailable 时不得沿用该证据声称当前代码通过。

### 5. 证据复用必须绑定完整身份

可复用证据至少要能核对：验证范围、命令、相关输入或代码 commit、环境类别、退出结果、日志/报告位置和已知限制。命令、代码、环境或覆盖范围变化即失效。证据只是技术事实，不是 OpenSpec 变更状态，也不能替代完成前新鲜验证门禁。

## 替代方案

- 直接复制 ai-pms 项目卡和 project.json：会违反源仓库业务知识分层，不采用。
- 在 registry 中保存完整传递依赖和构建拓扑：容易把声明误当真实执行图，先只做直接依赖，不采用更大模型。
- 让 `project-context` 自动执行 build/test 命令：扩大副作用和授权风险，不采用。
- 建全局测试结果数据库：会制造第二套状态和缓存真源，先用项目卡/证据文档约定，不采用。

## 风险与控制

- 依赖声明过期：输出仅称“声明依赖”，文档要求以代码、构建清单和契约复核。
- 命令包含敏感信息：命令必须单行并在文档中要求不写入凭据；工具只输出声明值，不读取输出或环境。
- 证据文档包含敏感日志：模板要求脱敏和最小化；安装器知识分层测试继续禁止源仓库业务事实。
- Git HEAD 比较误判：明确 current 不覆盖 dirty worktree；最终验证仍需按变更范围现跑。

## 实施边界

- 使用 `feature/extend-project-context-and-evidence-reuse` 隔离 worktree。
- 运行时行为变更按 TDD 先写失败测试。
- 所有随包复用文件与活动源保持字节同步，manifest 精确枚举新增模板和证据文档。
