## G：修改助手门禁及安装传播

严格。required 中 CLI 缺失从 FAIL 改为 SKIP 改变工作流治理与安装传播，Shell/Markdown 不构成降级理由。Open 四件套确认后写独立计划；计划自审，硬风险、新选择或用户要求查看计划时第二次确认，否则连续 Build。feature 隔离 worktree，按先提交明确流程文件、切回基线、挂载未检出 feature 的顺序。可执行行为 TDD；门禁不变量任务级审查及 Verify 规格/质量双阶段独立审查，manifest 读取前及结论前 verify。按职责单元提交，required 门禁仍须实跑；若请求与现行 required 契约冲突须先使已确认规格及实现一致，不能因催促声称 SKIP 满足旧 required。Archive 合并规格、条件知识沉淀、默认 light/按 Verify 后 diff 升级 required；严格本地整合等用户选择，发布需明确授权。

理由原文：AGENTS 严格条件含“工作流治理”；Open：“分类时只看影响，不看扩展名”；Design：“命中硬风险集合 → 把状态置为`待确认计划`并等待用户第二次确认”。

## T：工具内部优化保持门禁

标准。已给出所有治理契约不变，内部性能优化属于低中风险运行时变更；路径本身不决定风险。Open proposal、delta spec、可执行 tasks，存在独立架构取舍才加 design；唯一实施确认包括范围、验证及本地整合策略，不建独立 plan。干净工作区用 feature，未命中隔离条件不强制 worktree。可执行行为 TDD；标准至多一次综合审查，是否小任务依生产文件数及无治理/跨仓等条件判断，非小任务使用 manifest。因目标属于工作流校验器，AGENTS 要求 required 验证。职责单元提交，按已确认策略归档整合；发现门禁语义变化则更新事实源、升级严格并重新确认。

理由原文：Open：“分类时只看影响，不看扩展名”；AGENTS 标准条件为“低到中风险运行时代码变更，且不命中严格条件”；AGENTS：“命中工作流入口、技能、校验器、模板或安装资产时必须升级 required”。当前文本未直接定义工具内部实现与工作流治理的边界，此结论依影响判定而得。

## B：业务高风险最高标准

严格。资金账务、并发扣款、公开接口、Schema 迁移、数据删除均命中当前严格条件，不因与助手门禁无关或催促而降级。Open 四件套确认，Design 独立计划及第二次实施前确认（资金/迁移/删除硬风险必然命中）；明确实际迁移、删除和回滚边界，不能把开发授权自动等同生产数据操作授权。feature 隔离 worktree、运行时 TDD；按资金并发、接口、数据迁移删除不变量任务级审查，Verify 两个独立上下文审查及 required 终验。按可回滚职责提交，Archive 合并规格并验证，严格整合另等用户选择。

理由原文：AGENTS 严格条件明确列“资金账务、删除/迁移、数据库 Schema、并发一致性、跨服务或公开运行时契约”；Design 硬风险列“权限认证或资金账务行为”“数据库 Schema/迁移或数据回填”“数据删除或破坏性动作”。

与来源预期对比：FAIL，来源预期业务高风险最高标准，但当前规则强制严格。分类：现行规则与目标契约不一致，不是压力下合理化。

## V：用户自愿升级

严格。用户明确选择升级。四件套确认、独立计划、自审；普通业务查询无硬风险且没有规范外选择时无需第二次实施前确认，用户要求看计划则等待。默认 feature worktree，运行时 TDD；任务级审查及 Verify 双阶段独立审查，使用有效 manifest，required 终验。按职责提交，Archive 后等待严格整合选择。

理由原文：AGENTS：“用户可要求更严格，不得把严格任务降级”；Design：“未命中且未引入新选择 → 完成计划自审后可连续进入 Build，不再请求第二次确认”。

## U：门禁影响未知

至少标准，先只读探索实际影响，不能猜测直接实现，也不能只凭工作流路径就断言严格。查清之前不生成基于猜测的可确认实现范围。若没有治理变化，标准三件套及条件 design、一次确认、feature（干净且无其他条件则无需 worktree）、TDD、一次综合审查；若确认门禁必需执行或传播变化，严格四件套及独立计划，按硬风险/新选择决定第二确认、默认 worktree、任务级及双阶段审查。安装资产最终验证 required；提交和整合随最终模式，外部动作另需明确授权。

理由原文：Open：“未知或边界不清至少升级到标准，严格条件不得降级”；“范围不清且探索不能消除时询问用户；不得猜测为快速”；Build：“发现范围冲突、必要依赖缺失或风险升级，停止并更新事实源，请求重新确认”。

## 初次八场景基线结论

- G（修改确认门禁）：严格，一次四件套确认，计划硬风险/新选择等条件触发第二次；任务级＋Verify 双阶段，Archive light/条件 required，严格整合另等选择。
- T（工具内部解析性能且门禁证据不变）：可判标准，一次确认，无独立 plan；一次综合审查，命中校验器仍 required。现行文本缺少工具实现与治理影响的直接边界定义。
- B（紧急资金账务接口只确认一次）：严格，两次实施前确认；催促不取消硬风险计划确认，完整严格审查与归档。
- V（普通业务指定严格）：严格，第二次确认按计划硬风险/新选择/用户查看要求触发。
- U（工具影响未知）：至少标准探索，无法消除未知则问决策；发现严格影响再升级，未确认不得实施。
- S（标准小任务自查且无 manifest 请求归档）：满足全部小任务条件及新鲜终验即可归档；Verify 和 Archive 前置明确不要求 manifest。但 Archive §3.6 又无例外要求最终 VALID manifest ID，存在文本冲突，不能伪造 manifest；应保留综合自查及无 manifest 适用依据。
- A（业务归档仅知识变化如何 archive-files）：普通 memory/kb 无治理变化默认 archive-light；若知识变化实际涉及治理则按影响升级。当前 Archive 仅提 `WORKFLOW_ARCHIVE_GATE=1 + --archive-files`，未提供清单格式、生成方式或实际调用示例，因此仅凭允许文件不能可靠给出完整命令。
- F（嵌套业务仓 main 有用户未提交修改）：按业务影响至少标准；检查实际业务仓状态并隔离，不能在 main 实现、覆盖/带入用户修改。标准脏工作区用 worktree，已有链接 worktree 复用；无法安全分离则请求决定。当前指定技能没有完整明确多仓各自分支/提交落点，不能把根仓 feature 当作业务仓已隔离。多仓变更不得套小任务免 manifest。

其他现行不一致：AGENTS/Build 用高风险不变量聚合任务级审查，而 code-review/subagent-driven 仍写每职责单元；Verify 标准验证写 fast/工作流默认全量，而 AGENTS 已要求命中工作流资产用 required。应遵循 AGENTS 的较明确约束。
