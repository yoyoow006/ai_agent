# 设计

## 关键决策

把外部 `grill-with-docs` 的机制适配为 Open 阶段的“需求理解与追问”，而不是引入一个新技能或新状态文件。这样能复用其事实/决策分离、分轮 frontier、编号推荐答案和术语 sharpening，同时避免 `CONTEXT.md` 与 ADR 在本仓库形成另一套需求真源。

问题轮次以“当前已解锁的决策”为边界：先查权威事实，只有未知仍会改变目标、范围、风险、设计、验证或授权时才问；依赖用户本轮回答的问题留到下一轮。每个问题必须带证据、选项、推荐答案和影响，方便用户按编号简短回复。

确认结果按职责写入既有四件套：业务动机和边界进 proposal，可验证行为进 delta spec，取舍与术语进 design，执行与验证进 tasks。清晰请求不触发额外访谈，避免把需求理解变成流程税。

## 替代方案

- 直接移植 `grill-with-docs` 并创建 `CONTEXT.md`/ADR：访谈机制有价值，但会与 OpenSpec 状态真源重叠，且外部文档本身报告多写者漂移问题。
- 每次只问一个问题：交互安全但效率低；编号一轮更适合本仓库默认的执行型助手。
- 不设问题形状约束：现有规则已经允许询问，无法阻止问题倾倒或把事实推给用户。
- 为每个 proposal 增加固定“需求访谈”章节：会迫使清晰请求填充模板；改为按未知条件触发并把确认结果放到四件套既有职责位置。

## 风险与边界

- 这是流程文档与结构校验变更，不改变业务运行时代码、安装器事务行为或 CLI 参数。
- 需要防止新增规则被解释为所有任务都必须访谈；规格保留清晰请求直行场景。
- 双助手技能和可复用资产必须字节同步，公共 validator 需检查关键契约，防止只改一侧。
- 代理压力测试可能存在主观判断；测试记录须保留逐字回答和 PASS/FAIL 依据，并由独立审查核对。
